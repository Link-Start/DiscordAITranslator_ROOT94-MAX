# 已知限制与待验证事项

这里集中列出仍需观察的边界和有意暂缓的工作。只有取得具体证据后才开启相应修改；列出一项不表示它目前一定能复现为故障。已完成决策见[设计与经验笔记](../.agents/notes/README.md)，当前模块结构见[架构说明](architecture.zh-CN.md)，交付步骤见[开发与贡献指南](../CONTRIBUTING.md)。

<a id="observation-gated-work"></a>

## 需要证据后再推进的事项

| 观察范围 | 修改前需要取得的证据 |
| --- | --- |
| 生命周期与取消 | 具体的过期回调、任务泄漏或无效的供应商请求中止；包含请求/负责模块身份及任务注册表的清理路径 |
| 实际显示是否完成 | Store 修订及已挂载/屏外状态，区分数据已接受与显示已确认；区分翻译结果重绘和插件生命周期、全局设置引起的刷新 |
| 翻译语义质量 | 固定合成示例、响应 ID 对应关系；分别检查保护结构与实际含义 |
| 候选方案性能 | 可比较的端到端测量、实际网络请求数、有界预算及真实客户端表现 |
| 剩余大模块 | 明确的职责边界、已识别的生产调用者及回归覆盖；不安排无边界的运行时门面缩行任务 |
| Discord 兼容性 | 客户端更新后重新观察内部 Store 和快照结构；旧客户端证据不能证明新版本兼容 |

<a id="parked-work"></a>

## 暂缓的工作

自动连续读取多页历史的功能在此前回滚后继续暂缓。历史数量配置是上限，不代表可以持续读取直到凑满。默认启用实验功能或继续重做 UI，需要各自明确的决策和证据；当前已交付的 UI 不应被当成尚未实现的改版计划。

历史翻译的首轮请求已经使用并发上限；当前批量补译仍按批次串行执行。先保留现状，下一轮用同一频道、同一服务商记录首条显示、首轮结束、补译、显示确认和全部完成的端到端耗时，再决定是否并行化补译。优化必须继续遵守实时消息优先、全局供应商槽位、有界重试和服务商退避规则。

有明确边界的模块组装入口提取，以及直接通过 Store 订阅消息删除的工作都已完成。它们不代表上表中的独立观察项已关闭；应遵循[模块组装决策](../.agents/notes/implemented/architecture/2026-09-17-composition-root-boundary.md)及当前[生命周期职责](architecture.md#disable-stop-edit-and-cleanup)，不要重新开启旧阶段计划。
